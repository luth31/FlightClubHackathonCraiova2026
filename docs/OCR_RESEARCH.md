# Local PDF processing: research and implementation

Research and measurements: 31 October 2026. Tested on an Apple M3 Pro, macOS 26.2 arm64, Python 3.12.11; offline OCR also verified on the Linux arm64 API image.

## Decision

The closest match to the remembered Rust project is **[Firecrawl pdf-inspector](https://github.com/firecrawl/pdf-inspector)**. Its Python wheel exposes native extraction, classification, and per-page OCR recommendations. This is a strong match, not proof that it was the particular project seen on Twitter.

Implemented: **pdf-inspector 1.25.2 for routing + the existing PyMuPDF 1.26.7 for text/word geometry + Tesseract with bundled `ron+eng` fast models**. No external service, GPU, Rust compiler, Redis, or runtime model download is needed on the tested prebuilt wheels. Only optional Luna advice still makes an API call; it receives cached text and word IDs, not PDF bytes.

The page classifier runs on every page using `extract_pages_markdown`; quick document classification alone is not sufficient for a long mixed document. Pages with missing/broken text or a substantial image region get OCR. A native registration header does not hide a scanned body. Word boxes use the same unrotated PDF coordinate frame as the redaction editor.

## Candidates

| Candidate | Fit | Decision |
| --- | --- | --- |
| [pdf-inspector](https://github.com/firecrawl/pdf-inspector/blob/main/docs/python.md) | Rust, MIT, small Python wheel, per-page routing and encoding diagnostics | Use routing now. Its optional PP-OCRv6 path needs PDFium/ONNX runtime and model assets; unnecessary for this PDF-only integration. |
| [Kreuzberg](https://docs.kreuzberg.dev/guides/ocr/) | Rust core, many formats, Tesseract/PaddleOCR backends; very competitive native performance | Strong alternative if DOCX/email/many formats become a requirement. Current v4 is [LTS](https://docs.kreuzberg.dev/), with active development moving to Xberg. Adds a wider dependency surface than needed here. |
| [Ferrules](https://github.com/AmineDiro/ferrules) | Rust document parsing, PDFium, platform/model dependencies, GPL-3.0 | Less straightforward for the immediate macOS/Linux Romanian PDF workflow. Not benchmarked. |
| Existing PyMuPDF + Tesseract | Already used for PDF rendering/redaction; returns actual word rectangles | Reuse geometry and OCR instead of translating between two parsers' coordinate systems. |

“Local and free” means **no per-page service/API fee**. pdf-inspector is MIT; the bundled Tesseract data is Apache 2.0. PyMuPDF was already a dependency and has [AGPL/commercial licensing](https://pymupdf.readthedocs.io/en/latest/about.html#license-and-copyright); proprietary distribution must account for that choice. This implementation does not remove that existing licensing constraint.

## Measured performance

[Raw results](benchmarks/ocr-local-m3-pro.json), generated by `scripts/benchmark_extraction.py`. Three runs over the 148 existing PDFs (316 pages), in one process, cache disabled where supported. The measurements include library parsing but exclude worker process startup, database writes, HTTP, and queue delay. They are different output contracts, not equivalent quality rankings.

| Engine / output | Total for 148 PDFs | Typical median per document |
| --- | ---: | ---: |
| pdf-inspector native Markdown | 0.41–0.42 s | 2.6–2.7 ms |
| Kreuzberg native content, OCR disabled | 0.34–0.47 s | 2.2–2.3 ms |
| PyMuPDF native text | 1.22–1.25 s | 7.7–7.8 ms |
| Integrated routing + text + word geometry | 2.33–2.69 s | 14.8–16.2 ms |

The small synthetic Romanian scan took about **0.19–0.21 seconds** in the integrated engine. A more densely formatted corpus page took about **0.46–0.50 seconds** in earlier direct OCR trials. Offline Linux OCR of that corpus page took **0.51 seconds**. Browser smoke test: a 122 KB scan upload returned in **17 ms**, extraction took **160 ms**, and the UI refreshed automatically. These are local observations, not throughput guarantees.

## Accuracy and limits

The fixture script creates native, 200-DPI scan, 90-DPI scan, mixed-page, and hybrid documents with known Romanian text. The native fixture had 100% exact word recall. OCR on the clean scan had **89.36% exact word recall** and **100% accent-folded word recall**; the low-resolution fixture had **97.87% accent-folded recall**. Exact recall counts Romanian accents and legacy cedilla/comma differences as errors. Recall is multiset token overlap, not reading-order accuracy or a complete field-accuracy metric. These few synthetic fixtures cannot establish accuracy on a real airport archive.

`tessdata_best` was also tried directly on the clean scan. At 200 DPI it took 1.85 seconds versus approximately 0.20 seconds for `tessdata_fast`, and still missed some accents. The fast models are the better starting point here; [Tesseract documents this speed/accuracy tradeoff](https://tesseract-ocr.github.io/tessdoc/Data-Files.html).

OCR is marked for review. No calibrated confidence value is invented: `confidence` is null. Names, dates, account numbers, handwriting, stamps, skew, physical rotation, poor scans and complicated tables remain review-sensitive. This phase extracts text and word positions; it is not a table-to-spreadsheet parser, handwriting recognizer, deskew service, or new summarization feature.

## Persistence and consumer contract

- Uploads retain structural/security validation, then atomically store the immutable PDF/version and enqueue extraction. They no longer extract text synchronously or silently stop at page 100.
- `document_extractions` stores status, attempts, timestamps, source hash, pipeline version, complete text, and per-page text/word boxes/provenance. Its key is the PDF SHA-256 plus the pinned pipeline identifier. Identical bytes and metadata-only versions reuse the cache within the airport's isolated database.
- One background thread orchestrates a disposable parser subprocess. Native/OCR CPU work is outside the API process. Parser environment excludes API keys; all required OCR assets are bundled. The subprocess is not a hostile-code sandbox.
- A 300-second process timeout bounds jobs. Expired 360-second leases can be reclaimed after a restart, up to three interrupted attempts; explicit failures offer a user retry. Tokens prevent an obsolete worker from publishing over a reclaimed job.
- Publication joins against the current version hash under a database write lock. Late old-PDF results cannot overwrite a newer PDF. Manually edited fields and validated metadata remain unchanged. Search can index reviewed originals without changing their approval or bytes.
- Search uses SQLite FTS5. Metadata rules consume page text. Rule suggestions, interactive redaction and Luna consume the same cached text/geometry. Future summaries can call `cached_result(db, version)` after the caller's document access and integrity checks, preserving page numbers for citations.
- `GET /api/documents/{id}/extraction?page=1` returns status and one page of text. It checks document access and source integrity; technician roles retain their existing financial-text JSON restrictions. Full word geometry is only exposed through the existing authorized redaction API. `POST .../extraction/retry` requires edit access and only resets failed jobs.
- Originals and signatures are never rewritten by extraction. Scanned redaction uses cached boxes and removes image pixels in the derived copy; users still inspect every final page before sharing.

Limits: existing 25 MB / 1,000-page upload limits, 5 million extracted characters / 500,000 words, bounded OCR rendering (normally 200 DPI, at most approximately 12 megapixels), and a 100 MB serialized result limit. Excess/timeout produces an explicit failed status, not an apparently complete truncated document. This is an appropriate single-host queue for the current two-airport demo, not a distributed high-volume job platform. Each additional API process starts another worker.

## Reproduce

```bash
./scripts/dev.sh
# Or: ./scripts/start-demo.sh
backend/.venv/bin/pytest backend/tests -q
backend/.venv/bin/python scripts/benchmark_extraction.py
```

The benchmark writes disposable PDFs, page images, extracted results and timing JSON under `.runtime/ocr-benchmark/`. Optional engine comparison needs an isolated environment with `kreuzberg==4.10.4`, then `--compare`. No optional benchmark library is required to run the application. Language model provenance and SHA-256 values are in `data/tessdata/README.md`; model binaries and their license are checked in.

`FLYLEAF_EXTRACTION_ENABLED=false` disables the background runner for deterministic tests/maintenance. `FLYLEAF_TESSDATA_DIR` changes the local model directory. If substituting different models or extraction behavior, change `PIPELINE` too, so previous results do not masquerade as newly processed text.

Validation: 111 backend tests passed, including 12 new extraction tests; production TypeScript/Vite build passed. Chrome DevTools confirmed upload → queued → ready → automatic metadata → page text → full-text lookup. Linux Docker OCR passed with `--network none`. Additional deployment verification is recorded in `VERIFICATION.md`.
